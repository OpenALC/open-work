# 0001. 客户端 UI 策略

- **状态：** Accepted
- **日期：** 2026-11-07
- **关联：** 需求文档 §12；[roadmap](../development/roadmap.md) L0.5 / L5.1

---

## 背景

OpenWork 有两条前端线：

- **Web**（Vue 3 + TypeScript + Naive UI）：管理后台、IM、审批、工作流设计器、考勤报表
- **Flutter**（Dart）：Android / iOS / Windows / macOS / Linux，覆盖 IM、通讯录、审批、打卡、公告、WebView

两者在 IM、审批、考勤上有功能重叠，用户会在 Web 和手机之间来回切换。如果两端视觉不一致，切换成本会变成产品缺陷。

Flutter 本身既是渲染引擎也是 UI 框架，因此「选 UI 框架」实际是三层问题：底层用哪套设计语言、上层组件自建还是复用现成库、两端如何保持统一。

## 决策

### 1. 底层用 Material 3，不用 Cupertino

Flutter 内置的 Material 3 提供主题系统（`ColorScheme` / `TextTheme`）、状态层（涟漪、焦点）、无障碍与响应式断点。这些不要重写。

不使用 Cupertino 作为主风格：办公协作应用不应随宿主平台改变视觉；桌面端尤其不能出现 mac 风格控件。

### 2. 上层自建组件库

在 `apps/flutter/lib/design/` 下建立自有组件层，`ThemeData` 由设计令牌生成，业务页面只用自有组件，不直接用裸 Material widget。

**不引入第三方企业级 UI kit。** 现有库（TDesign Flutter、各类 Ant Design 移植）组件齐全但视觉是通用后台风：阴影多、圆角大、行高松。目标视觉恰好相反，覆盖成本高于自建。

允许引入的单点依赖：虚拟列表、图表、富文本编辑等有实质工程量的能力，用成熟库并包一层自有接口。

### 3. 跨端统一靠设计令牌，不靠共享组件

Web 是 CSS、Flutter 是 Dart，组件代码不可复用。复用的是**数值与语义**：

```text
packages/design-tokens/
├── tokens.json          单一来源（颜色、间距、圆角、字号、行高、阴影、动效时长）
├── build/css/tokens.css      → Web：CSS 变量 + Naive UI 主题覆盖
└── build/dart/tokens.dart    → Flutter：ThemeData 输入
```

规则：

- 任何颜色、间距、圆角、字号**不得在两端代码里硬编码**，必须取自令牌
- 令牌变更走一次生成，两端同时生效
- 组件变体命名两端一致（`primary` / `secondary` / `text` / `danger`），便于跨端开发
- 令牌文件是唯一真值，`build/` 下的产物为生成物，禁止手改

### 4. 视觉基调

参考飞书那种「轻、密、低对比」的办公协作观感，但不复制具体产品的视觉资产。落地时以取色与实测为准，此处只记录方向：

| 方面 | 方向 |
|---|---|
| 分隔 | 不用阴影，用 1px 低对比边框 |
| 圆角 | 小圆角（4–6px），不使用大圆角卡片 |
| 行高 | 列表行紧凑：IM 会话行 ≈64px，通讯录行 ≈48px |
| 字号 | 正文 14–15sp，字号阶梯窄 |
| 主色 | 单一品牌蓝，状态色克制 |
| 动效 | 150–200ms，只做透明度与位移 |

## 备选方案

| 方案 | 优点 | 缺点 | 为何不选 |
|---|---|---|---|
| 直接用 Material 默认主题 | 零成本 | 视觉是 Android 风，与 Web 端割裂 | 与「多端统一」目标冲突 |
| 用第三方 Flutter UI kit | 组件现成 | 视觉为通用后台风，深度定制成本高于自建 | 覆盖成本高，且受库版本牵制 |
| 两端各做一套设计 | 无跨端约束 | 维护两套视觉规范，必然漂移 | 违反产品原则 |
| Web 与 Flutter 共用 WebView 承载业务页面 | 一套 UI | 移动端体验差、原生能力受限 | 核心 IM 体验不可接受 |

## 后果

### 正面

- 两端共用一套数值，视觉漂移在源头被堵住
- 自有组件层不受第三方库破坏性升级影响
- 新端（如未来的平板/折叠屏）只需接令牌与组件层

### 负面 / 代价

- **组件要从零写。** 按钮、输入框、列表行、头像、气泡、标签页、弹窗，初期约需 15–20 个基础组件
- **设计令牌需要人工维护。** 新增语义要先定令牌再写组件，比直接写死颜色慢
- **Web 端需要覆盖 Naive UI 主题。** Naive UI 的 token 体系与自有令牌不是一一对应，需要一层映射，个别组件要改写
- 自建组件的无障碍与键盘导航需要自己保证

### 影响范围

`packages/design-tokens/`、`apps/flutter/lib/design/`、`apps/web/src/styles/`；所有前端页面不得硬编码视觉常量。

## 如何检查是否被遵守

- [ ] CI 中有 lint 规则：`apps/flutter/lib/**` 与 `apps/web/src/**`（除 design 目录）中出现十六进制颜色字面量即失败
- [ ] `packages/design-tokens/build/` 被重新生成后无 diff（生成物与源同步）
- [ ] 新增组件必须在两端按同名变体实现，或明确说明该组件仅单端存在
- [ ] 视觉走查：同一功能在 Web 与 Flutter 上的字号、行高、圆角、主色一致
