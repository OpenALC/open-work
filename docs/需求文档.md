# OpenWork — 产品需求与技术实现方案

> 项目名称：OpenWork（暂定）
>
> 项目定位：开源、轻量化、可扩展的企业协作与管理平台
>
> 开源许可证：Apache License 2.0
>
> 部署模式：多租户 SaaS + 企业独立私有化部署
>
> 核心技术：Go + MySQL + Redis + Vue 3 + Flutter
>
> 架构模式：模块化单体 + 独立实时通讯网关 + 异步任务执行器

---

# 一、项目概述

## 1.1 项目定位

OpenWork 是一个类似钉钉、飞书的开源企业协作平台，但不追求复制大型商业办公平台的全部功能。

项目专注于企业日常协作的核心需求，包括：

- 企业组织架构与人员管理
- 统一账号与多企业身份
- 角色与权限管理
- 即时通讯（IM）
- OA 审批与工作流
- 考勤、排班与工时管理
- 企业公告
- 聊天机器人与交互式消息卡片
- 企业应用 WebView 容器
- 开放 API、Webhook 与连接器
- 企业 ERP 等第三方业务系统集成

OpenWork 不内置复杂的 ERP、CRM、MES、WMS、财务等业务系统，而是通过开放平台支持企业自行开发和集成。

## 1.2 产品原则

1. **轻量化：** 专注企业协作基础能力，避免引入非必要业务模块。
2. **开源开放：** 采用 Apache-2.0 许可证，允许商业使用、私有化部署和二次开发。
3. **API First：** 核心能力通过标准化 API 提供，支持第三方应用集成。
4. **多租户：** 一个 SaaS 实例可以服务多个企业，企业之间的数据严格隔离。
5. **私有化：** 企业可以独立部署，不依赖官方 SaaS 服务。
6. **跨平台：** 覆盖 Android、iOS、Web、Windows、macOS、Linux。
7. **模块化：** 业务模块边界清晰，便于长期维护和社区扩展。
8. **可扩展：** 通过开放 API、连接器、SDK 和 WebView 扩展企业业务。
9. **安全性：** 认证、权限、数据隔离、审计与敏感信息保护作为基础能力。
10. **部署简便：** 优先降低中小企业和个人开发者的部署维护成本。

# 二、部署与租户模型

## 2.1 双部署模式

OpenWork 使用同一套核心代码支持两种部署模式。

### 多租户 SaaS

- 一个服务实例承载多个企业租户。
- 每个企业拥有独立组织架构、角色、权限、审批、考勤和应用配置。
- 用户可以通过一个账号加入多个企业。
- 支持同一 SaaS 实例内的受控跨企业通讯。
- 平台统一管理服务基础设施。

### 企业私有化部署

- 企业可以在自有服务器或私有云中独立部署。
- 使用独立数据库、缓存和文件存储。
- 支持本地账号认证与企业管理。
- 不强制依赖官方 SaaS 身份服务、消息服务或授权服务。
- 可以通过开放 API 对接企业内部 ERP 等系统。

### 跨实例扩展

不同私有化实例之间的通讯属于联邦通讯能力，架构上保留扩展空间。

跨实例通讯需要独立的身份信任、消息路由、实例发现与安全机制，不与同一 SaaS 内的跨租户通讯混为一谈。

## 2.2 核心身份模型

系统区分以下概念：

- `User`：自然人的全局账号。
- `Tenant`：企业租户。
- `Membership`：用户在某个企业中的成员身份。
- `Department`：企业内部部门。
- `Role`：企业内部角色。
- `Permission`：功能与操作权限。

一个 User 可以拥有多个 Membership。

每个 Membership 归属于一个 Tenant，并可关联多个 Department 和 Role。

不同企业中的成员身份、权限和业务数据相互独立。

私有化实例中的用户标识只在所属实例内具有确定意义，不假定不同实例的相同用户 ID 代表同一个自然人。

# 三、账号与组织架构

## 3.1 统一账号

支持：

- 用户注册、登录、退出
- 多设备登录
- 账号资料管理
- 修改密码与账号安全设置
- 加入多个企业
- 创建企业
- 企业邀请成员
- 企业切换
- 扫码登录
- 企业成员停用、离职和重新入职
- 登录会话管理

账号生命周期与企业成员生命周期相互独立。

员工从某企业离职，不影响其账号在其他企业中的使用。

## 3.2 组织架构

支持无限级部门树。

主要功能：

- 创建部门
- 编辑部门
- 删除或归档部门
- 调整部门层级
- 部门排序
- 部门负责人管理
- 员工加入或退出部门
- 员工跨部门调动
- 员工同时归属多个部门
- 设置主部门与兼职部门
- 组织架构查询
- 组织关系历史记录

组织架构作为部门成员关系的权威数据源。

### 推荐数据模型

- `tenants`
- `users`
- `tenant_memberships`
- `departments`
- `department_memberships`
- `department_managers`
- `department_closure`
- `organization_events`

部门树以 `parent_id` 为基础，复杂祖先与后代查询可通过 Closure Table 优化。

组织关系支持历史追溯，以便审批、考勤等模块还原业务发生时的组织状态。

## 3.3 组织自动群聊

创建部门时，自动创建对应的部门群聊。

部门群与组织架构绑定，成员由组织关系自动计算。

**父部门群包含本部门直属成员及全部下级部门成员，并按照企业成员身份去重。**

自动同步规则：

- 创建部门时自动创建部门群。
- 新成员加入部门后自动加入对应部门群及祖先部门群。
- 员工加入多个部门时，自动加入相关部门群。
- 员工退出部门时，重新计算群成员关系。
- 部门名称变化时同步群名称。
- 部门负责人变化时同步相关群管理权限。
- 部门移动时重新计算新旧祖先部门群。
- 部门删除时归档对应部门群。
- 员工离职时撤销其企业部门群访问权限。

部门群属于系统管理群，普通用户不能随意修改其组织成员关系。

普通自建群不受部门自动同步机制控制。

推荐采用组织变更事件、事务性 Outbox 和异步同步器维护群成员关系。

成员离职或权限撤销时，服务端立即阻止未授权访问，不依赖异步同步完成后才生效。

# 四、角色与权限管理

## 4.1 权限模型

采用：

**RBAC + Data Scope + Policy**

分别负责：

- RBAC：功能与操作权限。
- Data Scope：数据访问范围。
- Policy：企业安全与业务策略。

支持企业自行创建、编辑、删除角色，并为角色配置权限。

## 4.2 授权范围

支持：

- 企业级角色
- 部门级角色
- 资源级角色

权限可以分配给企业成员。

成员可拥有多个角色，实际权限根据角色作用域、数据范围和业务策略计算。

### 数据范围

支持：

- 仅本人
- 本部门
- 本部门及全部下级部门
- 指定部门
- 全企业
- 指定业务资源

## 4.3 权限粒度

支持：

- 菜单级权限
- 页面级权限
- 按钮级权限
- API 操作权限
- 数据范围权限
- 应用访问权限
- 连接器权限

推荐权限标识：

```text
organization.department.create
organization.department.update
organization.member.invite

im.group.create
im.group.member.manage

workflow.definition.publish
workflow.instance.approve

attendance.record.read
attendance.record.export

platform.app.manage
```

所有敏感权限必须在服务端验证。

客户端根据权限控制界面显示，但客户端判断不构成安全授权。

# 五、即时通讯 IM

## 5.1 基础通讯

支持：

- 一对一聊天
- 普通群聊
- 部门自动群聊
- 跨企业聊天
- 添加好友
- 删除好友
- 创建群聊
- 邀请和移除群成员
- 群主及群管理员
- 群名称、头像和公告
- 群成员权限管理

## 5.2 消息类型

支持：

- 文本消息
- Emoji
- 图片
- 文件
- 语音消息
- 结构化消息卡片
- 系统通知
- 机器人消息

消息功能包括：

- 消息撤回
- 删除个人消息记录
- 已读与未读状态
- 消息回执
- 消息引用与回复
- 消息转发
- @成员
- @全体成员
- 消息搜索
- 会话置顶
- 消息免打扰
- 历史消息分页
- 多设备消息同步
- 离线消息补拉
- 离线推送通知

语音与视频通话作为后续扩展能力。

## 5.3 跨企业通讯

允许跨企业添加好友、单聊及群聊，但受企业管理员策略控制。

支持：

- 完全禁止跨企业通讯
- 允许员工主动添加外部好友
- 仅允许与指定企业通讯
- 允许外部单聊但限制外部群聊
- 限制外部成员访问企业通讯录

跨企业通讯需要检查相关企业的授权策略。

企业内部业务会话以 Membership 为参与身份；个人好友关系可以基于 User 建立。

跨企业聊天需要明确用户对外展示的企业身份。

## 5.4 消息同步架构

采用：

**WebSocket 实时传输 + 服务端持久化 + HTTPS 增量同步**

核心设计：

- 服务端生成稳定消息 ID。
- 会话内部维护消息顺序。
- 客户端使用消息游标同步。
- 消息发送支持幂等键。
- 客户端断线后自动恢复连接。
- 重连后通过增量接口补拉消息。
- 移动端后台使用系统推送唤醒或通知。
- Redis 用于在线状态和临时数据。
- MySQL 保存持久化消息与会话元数据。

不依赖移动端长期后台 WebSocket 保持在线。

## 5.5 消息安全

采用：

- TLS 传输加密
- 服务端存储加密
- 附件访问授权
- 会话成员权限校验
- 消息访问范围控制
- 企业消息保留策略
- 敏感日志脱敏

默认不采用端到端加密 E2EE。

# 六、聊天机器人与消息卡片

## 6.1 机器人

支持企业自建机器人和第三方应用机器人。

机器人拥有独立身份与权限范围。

功能包括：

- 机器人注册
- 机器人授权
- 发送消息

- 群内机器人
- 机器人命令
- Webhook 回调
- 消息发送限流
- 机器人管理 API

支持：

- 标题
- 文本
- 图片
- 状态
- 按钮
- 链接
- 业务数据
- 操作回调

典型场景：

- ERP 订单审批

- 考勤异常通知
- 系统告警
- 业务状态更新

用户点击卡片按钮后，由服务端验证身份、权限及操作状态，再执行对应业务。

# 七、OA 审批与工作流

## 7.1 工作流定位

OpenWork Flow 是一个可视化、可扩展、事件驱动的企业审批与工作流系统。

支持内部 OA 审批和外部 ERP 等业务系统审批。

## 7.2 可视化流程设计器

支持拖拽式流程设计。

功能包括：

- 创建流程
- 编辑流程
- 删除或停用流程
- 流程分类
- 动态表单
- 节点拖拽
- 节点连接
- 条件分支
- 审批人配置
- 流程版本发布
- 流程历史版本
- 流程实例查询

推荐使用 Vue Flow 构建流程设计器。

已发布流程版本不可变，运行中的实例绑定对应版本。

## 7.3 工作流节点

支持：

- 开始节点
- 结束节点
- 人工审批节点
- 会签节点
- 或签节点
- 抄送节点
- 条件分支节点
- 自动审批节点
- 外部 API 查询节点
- 外部 API 执行节点

扩展节点包括：

- 并行分支
- 并行汇聚
- 定时等待
- 子流程

### 会签

所有指定审批人同意后通过。

默认任意审批人拒绝则节点拒绝。

### 或签

任意指定审批人同意后通过。

节点完成后，其他未完成审批任务自动关闭。

### 抄送

向指定人员发送审批信息，不阻塞流程。

### 自动审批

根据预定义规则、表单字段和外部数据自动执行审批决定。

## 7.4 审批操作

支持：

- 提交审批
- 同意
- 拒绝
- 撤回
- 抄送
- 查看审批进度
- 审批记录查询
- 审批代理
- 审批任务转交
- 管理员终止异常流程

撤回、撤销审批动作和管理员终止属于不同业务操作，分别管理权限和状态。

## 7.5 外部条件

审批条件支持：

- 表单字段
- 用户信息
- 部门信息
- 角色信息
- 外部 API 查询结果
- 多条件组合

外部 API 查询支持超时、错误处理、重试和结果映射。

## 7.6 工作流执行架构

采用持久化状态机。

核心组件：

- Workflow Designer
- Workflow Definition
- Workflow Engine
- Workflow Runtime
- Task Scheduler
- Connector Runtime
- Event Dispatcher

流程定义、实例、审批任务和连接器执行相互分离。

支持：

- 并发状态控制
- 执行持久化
- 幂等操作
- 异常恢复
- 延迟重试
- 人工处理
- 审批审计
- 外部操作补偿

推荐核心实体：

```text
workflow_definitions
workflow_versions
workflow_nodes
workflow_instances
workflow_tokens
workflow_tasks
workflow_actions
workflow_variables
workflow_executions
workflow_events
```

# 八、开放连接器平台

## 8.1 连接器定位

连接器用于将 OpenWork 与 ERP、MES、WMS、HR、财务及其他业务系统连接。

支持：

- 外部数据查询
- 外部业务执行
- 外部系统发起审批
- OpenWork 向外部系统推送事件
- 数据字段映射
- 身份映射
- 事件订阅
- 连接器版本管理
- 连接器授权
- 连接器日志

## 8.2 连接器类型

### HTTP 连接器

通过配置实现：

- 请求地址
- HTTP 方法
- 鉴权方式
- 请求参数
- 响应映射
- 超时
- 重试
- 错误处理

### 代码型连接器

第三方开发者通过 Connector SDK 编写连接器。

代码型连接器作为独立服务或进程运行，通过标准协议与 OpenWork 通讯。

不允许不可信连接器代码直接运行在 OpenWork 核心服务进程中。

## 8.3 连接器 SDK

采用语言无关的 HTTP/OpenAPI 协议定义连接器能力。

提供官方 SDK，支持：

- 应用认证
- API 调用
- Webhook 验签
- 事件处理
- 幂等请求
- 错误处理
- 数据模型封装

## 8.4 连接器安全

采用：

- OAuth 2.0 / 受限服务凭据
- Scope 授权
- 租户隔离
- 凭据加密存储
- Webhook 签名
- 时间戳与重放保护
- SSRF 防护
- 网络目标限制
- 请求超时
- 速率限制
- 执行审计
- 敏感数据脱敏

外部系统返回的数据不自动获得 OpenWork 内部管理权限。

# 九、考勤与排班

## 9.1 模块定位

OpenWork Attendance 提供企业考勤、排班、假期、工时和考勤报表能力。

## 9.2 打卡方式

支持：

1. GPS 定位打卡
2. Wi-Fi 打卡
3. 手机 App 人脸识别打卡
4. 外部人脸识别设备打卡
5. 外部考勤机打卡

### GPS 打卡

支持：

- 圆形地理围栏
- 多办公地点
- 定位距离判断
- 定位精度判断
- 企业自定义围栏范围
- 异常定位记录

### Wi-Fi 打卡

支持：

- SSID 白名单
- BSSID 白名单
- 接入点 MAC 地址辅助校验
- 网络环境信息记录
- 企业自定义 Wi-Fi 打卡策略

BSSID/MAC 校验仅作为辅助验证信号，不视为不可伪造的安全凭据。

移动端读取能力受 Android、iOS 系统权限及隐私策略限制，需要提供替代验证方式。

### 人脸识别

同时支持手机 App 和外部人脸识别设备。

手机端采用原生能力接口封装，并结合适当的活体检测与风险控制。

生物特征数据需要进行独立保护，支持必要的授权、删除和替代打卡方式。

### 外设考勤机

采用：

**统一设备接入协议 + 厂商适配器**

支持：

- 设备注册
- 设备认证
- 打卡事件上报
- 离线记录补传
- 数据去重
- 设备状态管理
- 厂商适配器扩展

## 9.3 统一打卡事件

所有打卡方式进入统一 AttendanceEvent 模型。

事件包含：

- 企业成员
- 打卡时间
- 打卡来源
- 设备信息
- 定位信息
- 网络验证信息
- 验证结果
- 风险信息

原始打卡事件尽量保持不可变。

补卡或修正通过新增修正记录实现。

## 9.4 排班管理

支持：

- Domain：业务规则。
- Repository：数据持久化。

- 业务规则不放入 HTTP Handler。
- 领域逻辑不直接依赖 Gin。

- 避免无意义抽象。
- 避免循环依赖。
- 不引入不必要的微服务。

# 十七、项目边界

OpenWork 的核心职责是：

**身份、组织、协作、审批、考勤与开放集成。**

不将以下系统作为内置核心业务：

- ERP
- CRM
- MES
- WMS
- TMS
- 财务核算
- 完整 HR 薪酬系统
- 复杂项目管理
- 大型文档协作套件

这些能力通过企业应用、开放 API、连接器和 WebView 扩展。

项目坚持轻量化核心、标准化接口、模块化实现和独立私有化部署，形成适合企业自主使用与社区二次开发的开源协作平台。

---

**OpenWork 的最终产品目标：构建一个以组织和身份为基础，以 IM、OA、考勤为核心，以开放 API、连接器和 WebView 为扩展机制的现代化开源企业协作平台。**
