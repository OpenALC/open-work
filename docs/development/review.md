# 审查

> 关联：[里程碑](roadmap.md) · [CI](ci.md) · [发版](release.md)

单人维护的项目。审查分两种：**我自己写代码时的自查**，和**别人提 PR 时的审**。

---

## 一、自己写完

合并前过一遍，五分钟：

- [ ] `make ci` 通过
- [ ] 需求对照：LT 里写的交付物都做了吗，有多做吗
- [ ] 测试是真的在验证行为吗，有没有偷偷放宽断言
- [ ] 新增查询都带 `tenant_id` 了吗
- [ ] 新增端点服务端校验权限了吗
- [ ] 错误都处理了吗，有没有吞掉
- [ ] 迁移能重复跑吗，有没有改到已合并的
- [ ] OpenAPI 更新了吗
- [ ] `CHANGELOG.md` 登记了吗
- [ ] 有没有调试残留、有没有把敏感字段打进日志

不用写报告。过一遍就够。

---

## 二、别人提 PR

判断三件事，按顺序：

1. **能不能用** — 解决问题了吗？跑起来是对的吗？有没有测试？CI 绿吗？
2. **会不会坏** — 碰了租户隔离、权限、迁移、凭据吗？碰了就要细看。
3. **好不好维护** — 跟现有代码一个路子吗？有没有引入奇怪依赖？范围是否合理？

### 直接拒的情况

- 引入 GPL/AGPL/SSPL 依赖
- 拼 SQL
- 不带 `tenant_id` 的查询
- 端点没有服务端权限校验
- 删了或跳过了测试
- 修改了已合并的迁移
- 夹带大量无关重构
- 提交了密钥

其余都能聊。范围大就说拆开，方向不对就说清楚原因，写法不喜欢但能用的就合。

### 回 PR 的格式

不用模板，说清楚就行：

```text
第 3 行这里跨租户查询没带 tenant_id，改成带 ctx 里的租户。
第 40 行这块建议拆出去单独 PR，跟这个功能没关系。
其余没问题，改完我合。
```

---

## 三、Issue

照常处理，不需要流程：能复现就修，修不了就说清楚为什么，不是核心范围的指向应用/连接器方案。

安全问题走 [SECURITY.md](../../SECURITY.md)，不在公开 issue 里讨论。

---

## 四、不做的事

- 不搞每日抽检、里程碑审查报告、审查效率指标
- 不引入自动审查 agent
- 不要求 CODEOWNERS、强制审批、多级审查
- 不维护"技术债盘点"表格

有需要再加，现在不需要。
